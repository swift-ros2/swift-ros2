# Architecture

swift-ros2 is a native Swift client for ROS 2 with one public API
(`ROS2Context` / `ROS2Node` / `ROS2Publisher` / `ROS2Subscription`, plus
services, actions, and parameters) fronting **two backends**:

1. **Wire path** — the pure-Swift XCDR v1 codec (from swift-ros2-rosidl) plus Zenoh / DDS wire codecs,
   speaking directly to `rmw_zenoh_cpp` (via zenoh-pico) or
   `rmw_cyclonedds_cpp` (via CycloneDDS). No `rcl`/`rclcpp` in the process.
   It is the internal fallback where RCL is not available: its clients
   (`ZenohClient`, `DDSClient`, the wire transport sessions) are `package`,
   and `SwiftROS2Zenoh` / `SwiftROS2DDS` are targets, not products. Retiring
   it on a platform in a later minor release is non-breaking. `SwiftROS2Wire`
   (here) and `SwiftROS2CDR` (in swift-ros2-rosidl) are public.
2. **RCL backend** — the real `rcl` + rmw stack, reached through the
   `CRclBridge` C shim. Publishing is serialized-only: messages are encoded in
   Swift and handed to the rcl serialized-message API, with no typed-publish
   path. On Apple it is in the build graph by default (opt out with
   `SWIFT_ROS2_DISABLE_RCL=1`); on Linux it is opt-in with
   `SWIFT_ROS2_ENABLE_RCL=1`. Windows and Android are wire-only. Its session
   (`RclTransportSession`) and client (`RclClient`) are `package`, and
   `SwiftROS2RCL` is a target, not a product.

`ROS2Context.makeDefaultSession(for:)` (`Sources/SwiftROS2/Context.swift`)
maps `TransportConfig.type` to a session, keyed on the build graph. The table
of which transport type reaches which backend on which graph is in the
[README](../README.md#backends-rcl-with-an-internal-wire-fallback). In that table,
"wire" is `ZenohTransportSession` / `DDSTransportSession`, "RCL" is
`RclTransportSession`, and "throws" is `TransportError.unsupportedFeature`.
Everything above the session seam — nodes, publishers, subscriptions,
services, actions, parameters — is shared.

## Target graph

    SwiftROS2 (umbrella: ROS2Context, ROS2Node, ROS2Publisher, ROS2Subscription,
     │         services / actions / parameters)
     ├── swift-ros2-rosidl (package dependency): SwiftROS2CDR, SwiftROS2Messages,
     │                         runtime interfaces
     ├── SwiftROS2Transport   — TransportSession seam, TransportConfig,
     │    │                     EntityManager, GIDManager, RclTransportSession
     │    └── SwiftROS2Wire   — Zenoh / DDS wire codecs, ROS2Distro wire extension
     │                         (depends on rosidl's SwiftROS2Messages)
     ├── SwiftROS2Zenoh ── CZenohBridge ── CZenohPico    (zenoh-pico FFI, internal)
     ├── SwiftROS2DDS   ── CDDSBridge   ── CCycloneDDS   (CycloneDDS FFI, internal; see the note below)
     └── SwiftROS2RCL   ── CRclBridge   ── CRos2         (rcl/rmw FFI; Apple default, Linux opt-in)

The only git submodules are the C sources `vendor/zenoh-pico` and
`vendor/cyclonedds` (for Linux source builds and the xcframework scripts); the
package carries no ROS IDL submodules. The code generator (`swift-ros2-gen`,
`SwiftROS2GenPlugin`) lives in swift-ros2-rosidl, and the standard message
types live in swift-ros2-common-interfaces, which this package never depends
on.

Tooling targets outside the runtime graph:

- `SwiftROS2ExampleInterfaces` and `SwiftROS2TestFixtures` — internal targets
  (not products) that hold the message and service types the examples and
  tests use. They are generated by `Scripts/regenerate-internal-types.sh` from
  the IDL pinned in `idl.lock`, which `Scripts/fetch-idl.sh` fetches into the
  gitignored `.idl/` directory. `rcl-registry-gen` reads the same IDL through
  `Scripts/regen-rcl-registry.sh`.
- `ParityMatrix` + `parity-tool` — the wire-vs-RCL parity matrix renderer
  behind [PARITY.md](PARITY.md).
- `SwiftROS2Bench` — internal benchmark / soak-analysis helpers (not a
  product; only in the RCL build graph, where `rcl-bench` and `rcl-soak` use it).

`CZenohBridge`, `CDDSBridge`, and `CRclBridge` are swift-ros2–authored C shims
around the vendor APIs. `CZenohPico`, `CCycloneDDS`, and `CRos2` are
link-only C targets — never `import`ed from Swift (a CI lint enforces this);
Swift reaches them through the bridge modules.

`CDDSBridge` links one CycloneDDS per graph. In the RCL-enabled cyclonedds
graph on Apple it links the CycloneDDS inside `CRos2` instead of `CCycloneDDS`,
so the binary carries a single CycloneDDS; wire-only graphs
(`SWIFT_ROS2_DISABLE_RCL=1`) and the zenoh variant link `CCycloneDDS`.

## Platform arms

`Package.swift` selects one of four arms via the `SWIFT_ROS2_TARGET_OS` env
override (allow-list `{apple, linux, windows, android}`, mandatory for
cross-compiles) or the host `#if os(...)` fallback:

| Arm | zenoh-pico | CycloneDDS | RCL |
|-----|------------|------------|-----|
| Apple | `binaryTarget` xcframework from the pinned GitHub release | `binaryTarget` xcframework | `binaryTarget` xcframework from the release URL (default; `SWIFT_ROS2_DISABLE_RCL=1` opts out) |
| Linux | source build of `vendor/zenoh-pico` (unix backend) | `systemLibrary` via `pkg-config` | system ROS 2 install (opt-in, `SWIFT_ROS2_ENABLE_RCL=1`) |
| Windows | source build (windows backend, Winsock + Iphlpapi) | `systemLibrary` via vcpkg (`CYCLONEDDS_DIR`; Zenoh-only when unset) | none |
| Android | source build (Bionic, unix backend) | none | none |

The `SwiftROS2` umbrella builds on every arm. `SwiftROS2DDS` exists only
where CycloneDDS is consumable; on Android (and Windows without
`CYCLONEDDS_DIR`) the umbrella is Zenoh-only and `.dds` transports throw
`TransportError.unsupportedFeature`. Consumers depend on the `SwiftROS2`
product on every arm — the wire targets are not products.

## RCL backend provisioning

On by default on Apple (since 1.4.0; `SWIFT_ROS2_DISABLE_RCL=1` opts out)
and opt-in on Linux (`SWIFT_ROS2_ENABLE_RCL=1`). The rmw selection differs per
platform:

- **Apple** — `CRos2` is a URL-based `binaryTarget`: the prebuilt
  xcframework is a release artifact (built by `Scripts/build-ros2-xcframework.sh`
  in `release-xcframework.yml`) resolved from the pinned release URL +
  checksum. `SWIFT_ROS2_RCL_LOCAL=1` resolves it
  from a local `build/ros2*/` instead (CI and ROS 2 cross-build iteration).
  The slices are arm64-only: x86_64 builds (Intel Macs, x86_64 simulators,
  universal Mac Catalyst / macOS archives) need `SWIFT_ROS2_DISABLE_RCL=1` or an
  arm64-only build.
  The rmw is **baked per build variant**, selected by `SWIFT_ROS2_RCL_RMW`:
  `cyclonedds` (default) → `CRos2.xcframework`, `zenoh` →
  `CRos2Zenoh.xcframework` (no visionOS slice). The zenoh variant bundles
  zenoh-c, which collides with zenoh-pico's C symbols, so that variant carves
  the zenoh-pico wire family out of the build graph and `.zenoh` configs are
  served by rcl + `rmw_zenoh_cpp` instead; `.rcl` / `.rclUnicast` throw there,
  since they target `rmw_cyclonedds_cpp`.
- **Linux** — `CRos2` is a `systemLibrary` over the system ROS 2 install,
  located through `ROS2_RCL_PREFIX` (colon-separated ament prefix list,
  defaulting to `/opt/ros/${ROS_DISTRO:-jazzy}`). rcl has no pkg-config, so
  the manifest injects `-I`/`-L`/`-l` flags directly. The rmw is selected **at
  runtime, once per process**, from the transport type: `.zenoh` →
  `rmw_zenoh_cpp`, `.dds` / `.rcl` → `rmw_cyclonedds_cpp`. Because
  `RMW_IMPLEMENTATION` is process-global, one process serves one rmw — mixing
  `.zenoh` and `.dds` contexts in a Linux RCL process is unsupported (the wire
  path and Apple builds have no such restriction).

Per-backend behavioral parity is tracked feature-by-feature in
[PARITY.md](PARITY.md).

## Subscription delivery

Every transport hands a subscription the same thing: the raw CDR payload of
each sample, on its own receive thread (a zenoh-pico read task, a CycloneDDS
listener thread or an rcl wait thread). What happens next lives in
`ROS2Subscription` (`Sources/SwiftROS2/Subscription.swift`), above the session
seam, so both delivery modes behave the same on every transport:

    transport receive thread
     │  raw payload
     ▼
    ROS2Subscription.receivePayload
     ├── .stream      decode → yield into `messages` (newest 100) → handler,
     │                all on the receive thread
     └── .latestOnly  swap the payload into a one-message slot under the lock,
                      queue a drain if none is queued, return
                       │
                       ▼
                      serial delivery queue `swift-ros2.delivery.<topic>`:
                      take the slot → decode → handler, until the slot is empty

- **`.latestOnly` work on the receive thread is O(1)**: a slot swap and at most
  one `DispatchQueue.async`. It never decodes, never calls user code and never
  waits, so a slow handler cannot stall the session's read task or a listener
  thread. A replaced payload is freed outside the lock and never decoded.
- **One drain at a time.** A drain is queued when a payload lands with a
  handler set and no drain queued, or when `onMessage(_:)` finds a waiting
  payload. It loops until the slot is empty, so the handler is serial and sees
  messages in arrival order. Memory is bounded by one waiting payload plus the
  message in the handler.
- **History.** `ROS2Node` gives a `.latestOnly` subscriber `keepLast(1)`: wire
  Zenoh then asks the publishers' caches for one sample (`_max=1`), and a DDS or
  rmw reader keeps one. Reliability and durability pass through unchanged.
- **Handler at creation.** `ROS2Node` builds the `ROS2Subscription`, with its
  delivery mode and handler, before it calls `createSubscriber`, and the
  transport handler captures it weakly. A sample delivered while the transport
  subscriber is being created (a CycloneDDS transient-local replay, an rcl wait
  thread that starts inside `crcl_subscription_create`, a wire Zenoh history
  reply) therefore finds the handler.
- **Cancel.** `cancel()` marks the subscription closed and empties the slot under
  the lock, then closes the transport subscriber outside it. The drain checks
  the closed flag before each handler call, so at most one call that already
  passed the check runs after `cancel()` returns.

## Topic graph

`ROS2Context.topicGraph()` (`Sources/SwiftROS2/TopicGraph.swift`) downcasts its
session to the `package` protocol `TopicGraphSession`
(`Sources/SwiftROS2Transport/TopicGraphSession.swift`), as `ROS2Node` does for
`NodeScopedSession`, and throws `TransportError.unsupportedFeature("topic graph")`
when the cast fails. A session returns a flat list of `GraphPublisherEndpoint`
values (ROS topic name, ROS type, reliability, durability, node name and
namespace); the umbrella groups them by name and type, maps the QoS to the
public enums and sorts, once for every transport. Each transport maps a QoS
value it cannot read as RELIABLE or TRANSIENT_LOCAL to best effort or volatile,
and keeps a publisher it cannot attribute with `_NODE_NAME_UNKNOWN_` /
`_NODE_NAMESPACE_UNKNOWN_`.

- **Wire Zenoh** (`ZenohTransportSession+Graph.swift`,
  `Internal/ZenohGraphQueries.swift`). One liveliness query per call on
  `@ros2_lv/<domain>/*/*/*/MP/**`, answered by the router, merged with the
  session's own `MP` tokens (kept while their handles live) and parsed by
  `ZenohWireCodec.parsePublisherToken(_:)`, which demangles the names and turns
  the DDS type name into the ROS one (`TypeNameConverter.toROSTypeName`).
  zenoh-pico ignores a liveliness query's timeout, so `ZenohGraphQueries`
  enforces its own limits under one lock. Concurrent calls join the newest
  query, and a call gives up after 1.5 s (`.sessionUnhealthy`, never a partial
  list). A query past its deadline that still has no final makes new calls
  fail at once until it is 10 s old; then it is abandoned and the next call
  starts a new one. Three
  abandoned queries mark the session graph-stalled, which makes `isConnected`
  false until `close()`. Publishing does not read `isConnected`, and entity
  creation checks the zenoh-pico session health directly, so a graph-stalled
  session keeps working. The reply callbacks run on zenoh-pico's read task and
  only append under the lock.
- **Wire DDS** (`DDSTransportSession+Graph.swift`, `dds_bridge_enumerate_publications`
  in `CDDSBridge`). The first call creates readers of the builtin
  `DCPSPublication` and `DCPSParticipant` topics on the session's participant;
  each call reads their alive instances with loaned samples (and takes the
  disposed ones) on the session's serial queue `swift-ros2.graph.dds`. Only `rt/`
  topics are listed. Writers are attributed to nodes through the
  `ros_discovery_info` records the session reads from `open()`
  (`DDSDiscoveryInfoCache`, 16- and 24-byte gids, pruned to the participants
  still present), and the writers of this process's wire DDS sessions directly
  from their `DDSParticipantGraph` through a process registry, since the
  CycloneDDS domain is process-global.
- **RCL** (`RclTransportSession+Graph.swift`, `crcl_graph_snapshot` in
  `CRclBridge`). `rcl_get_topic_names_and_types`, then
  `rcl_get_publishers_info_by_topic` per name, through an internal node
  (`_swift_ros2_graph` in `/`) that the first call creates and `close()` destroys
  before the context. rcl's graph calls are not thread-safe, so every snapshot
  runs under one lock on the session's serial queue `swift-ros2.graph.rcl`. rmw
  returns ROS names and types; only RELIABLE and TRANSIENT_LOCAL map to reliable
  and transient-local.

None of the three reads blocks a thread of the Swift concurrency cooperative
pool: the wire Zenoh call suspends on a continuation that the query's callbacks
or its deadline resume, and the DDS and RCL reads run on their session's serial
queue.

## Wire format contract (wire path)

The canonical guardrails are the golden tests under `Tests/SwiftROS2WireTests/`
here and the golden CDR tests in swift-ros2-rosidl. In brief:

- **Key expression** —
  `<domain>/<namespace>/<topic>/<dds_type_name>/<type_hash-or-TypeHashNotSupported>`,
  DDS type name in the `::msg::dds_::Type_` form. Humble always emits
  `TypeHashNotSupported`; Jazzy+ drops the segment when the hash is absent.
- **Attachment** (33 bytes) — `seq` (int64 LE) + `timestamp_ns` (int64 LE) +
  LEB128 byte `0x10` + 16-byte GID.
- **CDR** — XCDR v1, explicit little-endian, 4-byte encapsulation header
  `00 01 00 00`. Fixed-size arrays serialize without a length prefix;
  sequences carry a 4-byte `uint32` length prefix.

The RCL backend reuses the same `SwiftROS2CDR` encoder / decoder (from
swift-ros2-rosidl): messages are serialized in Swift and handed to
`rcl_publish_serialized_message`
(taken back via `rcl_take_serialized_message`), with `rosidl` typesupport
resolved per type when the rcl entities are created. The key-expression and
attachment rules above are wire-path-only — on the RCL backend the rmw owns
discovery and metadata.
